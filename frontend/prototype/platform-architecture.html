01

Tổng quan giải pháp

Nền tảng gồm 5 module tách bạch trách nhiệm, nói chuyện với nhau chỉ qua AgentGateway. Không có kết nối tắt giữa Agent và bất kỳ hệ thống nghiệp vụ hay LLM nào — mọi lệnh gọi tool, mọi lệnh gọi model đều đi qua một control-plane duy nhất để xác thực, phân quyền, áp policy và ghi vết.

MODULE 1

Backend tiếp nhận

Nhận hồ sơ qua Kafka (message chứa file id), lưu kết quả từng task, expose API cho UI & tool cập nhật kết quả cho Agent.

MODULE 2

Agent

Runtime chạy các agent process — skill, planner, MCP tool client. Không tự kết nối trực tiếp hệ thống nào.

MODULE 3

Knowledge (GraphRAG)

Hồ sơ phương án vay, thông tin trích xuất, tri thức chuyên gia, bài học lịch sử — hợp nhất vào knowledge graph + vector index.

MODULE 4

LOS (hệ thống lõi)

Cung cấp tool để Agent lấy thông tin phương án vay hoặc thông tin RM cập nhật, và các nghiệp vụ tín dụng khác.

MODULE 5

AgentGateway

Cấu hình & kiểm soát mọi tool (LOS, Backend, Knowledge, Module Proxy…) và mọi lệnh gọi LLM đi qua một tầng duy nhất.

Phân biệt Module 1 và Module 4: Module 1 (Backend tiếp nhận) là lớp mới, đóng vai "bàn giao việc" — nhận sự kiện hồ sơ, sinh task cho Agent, lưu và hiển thị kết quả từng task. Module 4 (LOS lõi) là hệ thống nghiệp vụ tín dụng đã có — nắm dữ liệu phương án vay, khách hàng, RM, tài sản bảo đảm... Agent gọi cả hai, nhưng với hai mục đích khác nhau: Module 1 để báo cáo tiến độ công việc của chính Agent, Module 4 để lấy/ghi dữ liệu nghiệp vụ.
02

Kiến trúc theo mô hình C4

Ba lớp phóng to dần: Context (hệ thống nào nói với hệ thống nào) → Container (bên trong "Nền tảng Agent Thẩm định" có những khối chạy độc lập nào) → Component (bên trong một khối, ví dụ Backend Service, có những thành phần nào). Ranh giới hệ thống ở Context khớp đúng ranh giới 2 team ở mục Phân công 2 team.

Level 1 — System Context

Nhìn từ xa nhất: người dùng, hai hệ thống (mỗi hệ thống do một team sở hữu), và LLM Providers bên ngoài.

Level 2 — Container (bên trong "Nền tảng Agent Thẩm định")

Phóng to hệ thống đang thiết kế: 6 container độc lập (deploy riêng được), khớp đúng Module 1/2/3/5 đã mô tả ở các mục trước.

Level 3 — Component (bên trong container "Backend Service")

Phóng to tiếp container mà bạn sẽ làm đầu tiên (Module 1), để team AI Agent bắt tay code được ngay.

Ký hiệu C4: [Person] người dùng · [Software System] hệ thống hoàn chỉnh, một team sở hữu · [Container] ứng dụng/dịch vụ/CSDL deploy độc lập bên trong một hệ thống · [Component] nhóm logic bên trong một container. Mỗi mức chỉ phóng to một khối của mức trên — đúng nguyên tắc C4, không vẽ mọi thứ trong một hình.

04

Module 1 — Backend tiếp nhận & điều phối task

Cửa vào của toàn hệ thống. Nhận hồ sơ qua Kafka, tạo và theo dõi task cho Agent, lưu kết quả, và là nguồn dữ liệu cho giao diện xem kết quả từng task.

Trách nhiệm

  • Kafka consumer: lắng nghe topic tiếp nhận hồ sơ, message chứa case_id và danh sách file_id.
  • Case/Task orchestration: tạo case, sinh danh sách task theo skill cần chạy, theo dõi trạng thái.
  • Task/Result store: lưu kết quả mỗi task — nội dung, độ tin cậy, nguồn dữ liệu (source_refs), phiên bản.
  • API cho giao diện: phục vụ UI kiểu appraisal-agent.html / panel trong los-embedded.html — danh sách task, chi tiết, tiến độ tổng.
  • Tool cập nhật kết quả: expose hành động ghi (qua Gateway) để Agent gọi vào lưu kết quả từng task khi hoàn tất.

Message Kafka — tiếp nhận hồ sơ

// topic: los.case.intake
{
  event: "case.intake.received",
  case_id: "LOS-2026-04871",
  file_ids: ["doc_8841", "doc_8842", "doc_8843"],
  product_type: "working_capital_khdn",
  source_channel: "branch-portal",
  submitted_by: "rm_2291",
  submitted_at: "2026-08-26T08:12:00+07:00"
}

Mô hình dữ liệu chính

Thực thểTrường then chốt
Casecase_id, status, file_ids[], created_at
Tasktask_id, case_id, skill, status, confidence, assignee
TaskResulttask_id, result, source_refs[], version, produced_by

API & tool phơi ra (đăng ký trên AgentGateway)

Giao diệnDùng choGhi chú
GET /cases/{id}/tasks UI hiển thị tiến độ (tiles, danh sách task) Đọc trực tiếp, không qua Gateway — UI thuộc "bên trong" Backend.
GET /tasks/{id}/result UI hiển thị chi tiết một task khi mở rộng dòng Trả kèm confidence, source_refs như trong appraisal-agent.html.
backend.create_tasks(case_id, plan) Agent Orchestrator sinh kế hoạch task Tool ghi — qua Gateway, gắn agent_id + on_behalf_of.
backend.update_task_result(task_id, result, confidence, source_refs) Tool Agent gọi để lưu kết quả từng task Idempotent theo task_id + version. Đây là tool trọng tâm của Module 1.
backend.get_case_context(case_id) Agent lấy lại ngữ cảnh khi tiếp tục xử lý Trả danh sách task đã/chưa xong — dùng khi resume.
05

Module 2 — Agent

Nơi chạy các agent process. Mỗi agent có một tập skill và chỉ tương tác với thế giới ngoài qua tool MCP đăng ký trên AgentGateway — không tự giữ credential hay địa chỉ hệ thống nào.

Thành phần runtime

  • Planner/Orchestrator: nhận sự kiện case.intake.received (qua Backend), sinh kế hoạch task theo loại hồ sơ.
  • Skill: đơn vị nghiệp vụ có thể tái sử dụng — ví dụ "Phân tích BCTC & DSCR", "Rà soát pháp lý", "Định giá TSBĐ sơ bộ", "Soạn tờ trình".
  • MCP tool client: một client duy nhất, trỏ về AgentGateway; danh mục tool nạp động từ Gateway theo quyền được cấp.
  • Bộ nhớ phiên: ngữ cảnh case đang xử lý + kết quả các skill đã chạy trong phiên, tách khỏi Knowledge (dài hạn).

Ví dụ khai báo một skill

// skill: spreading_and_dscr
{
  skill_id: "spreading_and_dscr",
  inputs: ["case_id"],
  tools: [
    "los.document_extract",
    "los.spreading_compute_ratios",
    "knowledge.get_industry_benchmarks",
    "backend.update_task_result"
  ],
  output_schema: "FinancialRatioResult",
  needs_human_review_if: "dscr < policy_min"
}
Nguyên tắc: Agent Runtime không phân biệt được một tool là của Backend, Knowledge, hay LOS — với Agent, tất cả chỉ là "tool có sẵn trên Gateway". Việc thêm hệ thống mới (một Module Proxy khác, một nguồn dữ liệu mới) chỉ cần đăng ký trên Gateway, không cần đổi mã Agent.
06

Module 3 — Knowledge (GraphRAG)

Nơi hợp nhất 4 nguồn tri thức mà Agent cần để suy luận có ngữ cảnh: hồ sơ phương án vay, thông tin đã trích xuất, tri thức chuyên gia, và bài học từ các hồ sơ lịch sử. Kết hợp knowledge graph (quan hệ thực thể) với vector search (tương đồng ngữ nghĩa) — đúng mô hình GraphRAG.

Pipeline nạp & truy hồi tri thức

1

Nạp nguồn (ingest)

Knowledge Đồng bộ từ Backend (kết quả task, source_refs) và LOS (phương án vay, hồ sơ đã duyệt), nhập tri thức chuyên gia (playbook, ghi chú thẩm định đã chuẩn hoá).

2

Trích xuất thực thể & quan hệ

Knowledge Nhận diện thực thể (Bên vay, Phương án vay, TSBĐ, Bên liên quan, Quy tắc chính sách, Case lịch sử) và quan hệ giữa chúng (vay/bảo đảm/liên quan/áp dụng quy tắc).

3

Xây knowledge graph + vector index

Knowledge Ghi vào graph store (quan hệ tường minh: nhóm KH liên quan, tiền lệ áp dụng quy tắc) và vector store (embedding case/đoạn văn bản để tìm case/tình huống tương tự).

4

Truy hồi kết hợp (GraphRAG)

Knowledge Khi Agent hỏi, hệ thống vừa duyệt graph (quan hệ trực tiếp) vừa tìm tương đồng vector (case gần giống), tổng hợp thành ngữ cảnh có trích dẫn nguồn trả về Agent.

Tool phơi ra (qua Gateway)

  • knowledge.query_case_context(case_id) — tổng hợp phương án vay + trích xuất liên quan.
  • knowledge.find_similar_cases(features, k) — case lịch sử gần giống (vector + graph).
  • knowledge.get_expert_notes(topic) — ghi chú/playbook chuyên gia theo chủ đề.
  • knowledge.get_lessons_learned(skill_id) — điểm khác biệt nháp/kết luận cuối từng skill.
  • knowledge.explain_relation(entity_a, entity_b) — đường quan hệ trong graph, có trích dẫn.

Vì sao cần GraphRAG, không chỉ RAG thuần vector

  • Nhóm khách hàng liên quan, sở hữu chéo là quan hệ nhiều bước — vector search một mình không truy được đường liên kết.
  • Trả lời cần trích dẫn theo cấu trúc (case nào, quy tắc nào), không chỉ đoạn văn bản gần giống.
  • Cho phép Agent hỏi "case tương tự trước đây xử lý sao" bằng cả ngữ nghĩa và quan hệ tường minh.
07

Module 4 — LOS cung cấp tool nghiệp vụ

Hệ thống LOS hiện hữu, giữ vai trò system of record. Không đổi kiến trúc LOS — chỉ thêm một lớp tool (MCP) phơi các năng lực cần cho Agent, đăng ký qua AgentGateway.

Tool tiêu biểuTrả vềGhi chú kiểm soát
los.get_loan_plan(case_id) Đề nghị cấp TD, mục đích vay, cấu trúc, TSBĐ Chỉ đọc. Nguồn cho phần "Phương án sử dụng vốn" hiển thị trong hồ sơ.
los.get_rm_updates(case_id) Ghi chú/cập nhật của RM trong quá trình xử lý Chỉ đọc. Giúp Agent nắm thông tin RM bổ sung ngoài hồ sơ gốc.
party.get_related_group(borrower_id) Nhóm khách hàng liên quan, sở hữu chéo Đầu vào bắt buộc cho kiểm tra giới hạn cấp TD.
collateral.estimate_value(collateral_id) Định giá tham chiếu sơ bộ TSBĐ Ước tính; định giá chính thức qua request_valuation (proposed action).
compliance.evaluate(proposal) Phán quyết pass/fail/review kèm rule_id, trích dẫn Chốt chặn riêng cho mọi nội dung tín dụng — xem chi tiết ở agent-los-architecture.html.
workflow.propose(action) Đưa hành động rủi ro cao vào hàng đợi duyệt Không tự thực thi — luôn qua Approval Broker của LOS.

Danh mục đầy đủ (document.*, spreading.*, bureau.*, party.*, collateral.*, creditmemo.*, workflow.*, notify.*, audit.*, compliance.*) và 10 nguyên tắc thiết kế tool đã có ở agent-los-architecture.html — module này chỉ bổ sung los.get_loan_plan và los.get_rm_updates, đồng thời chỉ rõ toàn bộ danh mục được đăng ký trên AgentGateway thay vì Agent gọi trực tiếp MCP server của LOS.

08

Module 5 — AgentGateway

Tầng kiểm soát trung tâm (theo mô hình AgentGateway của Linux Foundation) — điểm tập trung duy nhất mà mọi tool call và mọi lệnh gọi LLM phải đi qua, bất kể tool đó thuộc Backend, LOS, Knowledge, hay một Module Proxy/hệ thống ngoài khác được nối vào sau này.

Vai trò

  • Registry & federation tool: hợp nhất nhiều MCP server (Backend, Knowledge, LOS, Module Proxy…) thành một danh mục tool duy nhất mà Agent thấy được, theo quyền được cấp.
  • AuthN/AuthZ tập trung: xác thực danh tính Agent, áp on_behalf_of người dùng, RBAC theo từng tool/scope — không hệ thống downstream nào tự kiểm tra quyền riêng.
  • Định tuyến & quản trị LLM: một điểm cấu hình cho nhiều model/provider — chọn model theo tác vụ, fallback khi lỗi, cache theo prompt, kiểm soát chi phí/token.
  • Policy runtime: rate limit, chặn tool nguy hiểm theo ngữ cảnh, ép hành động rủi ro cao thành proposed_action trước khi tới hệ thống đích.
  • Observability & audit bất biến: log mọi lệnh gọi (tool, tham số, kết quả, model, token) — một nguồn duy nhất phục vụ thanh tra, thay vì rải rác ở từng hệ thống.

Những gì được đăng ký qua Gateway

backend.* knowledge.* los.* / party.* / collateral.* / creditmemo.* compliance.* Module Proxy / hệ thống ngoài khác LLM providers (nhiều model)

Ví dụ policy cấu hình (minh hoạ)

// policy: agent "trolythamdinh" → tool "workflow.propose"
{
  tool: "workflow.propose",
  effect: "require_human_approval",
  rate_limit: "20/hour",
  route: "los-mcp-server:8443"
}
// policy: model routing
{ task: "spreading_and_dscr", model: "reasoning-tier-1", fallback: "reasoning-tier-2" }

Luồng end-to-end

Ví dụ hồ sơ LOS-2026-04871 đi qua đủ 5 module, từ lúc Kafka nhận message tới khi kết quả hiển thị trên panel Agent trong LOS.

Sơ đồ minh hoạ: dòng dữ liệu cho Task 01 & Task 02

Bám sát đúng 2 task đầu của hồ sơ trong appraisal-agent.html — mỗi khối là một bước xử lý cụ thể, màu khối cho biết hệ thống nào đang cầm dữ liệu tại bước đó.

10

Vận hành, bảo mật & khả năng mở rộng

Các nguyên tắc bắt buộc để kiến trúc 5 module này an toàn và kiểm toán được trong môi trường ngân hàng.

01
Một điểm vào duy nhất cho Agent. Agent Runtime không giữ credential trực tiếp tới Backend/Knowledge/LOS — chỉ có cấu hình trỏ tới AgentGateway.
02
Idempotency cho mọi lệnh ghi. backend.update_task_result, backend.create_tasks nhận idempotency_key/version — retry an toàn khi Kafka hoặc mạng gián đoạn.
03
Kafka có DLQ & replay. Message lỗi (file_id không hợp lệ, thiếu case) vào dead-letter queue; có khả năng replay theo case_id khi cần điều tra.
04
Audit trace hợp nhất tại Gateway. Không log rải rác ở từng hệ thống — một nguồn duy nhất, bất biến, phục vụ thanh tra và tái hiện sự cố.
05
Knowledge tách "sự thật" và "gợi ý". Dữ liệu từ LOS/Backend (nguồn gốc rõ) và tri thức tổng hợp/case tương tự (chỉ để tham khảo) phải phân loại rõ, không trộn lẫn khi trả cho Agent.
06
Định tuyến LLM có fallback & giới hạn chi phí. Gateway cấu hình model theo tác vụ, không hard-code trong Agent — đổi model không cần deploy lại Agent.
07
Hành động rủi ro cao luôn qua Approval Broker của LOS. Dù đi qua Gateway, các tool ghi có tác động ngoài (gửi yêu cầu, đổi trạng thái hồ sơ) vẫn phải là proposed_action.
08
Mở rộng bằng đăng ký, không bằng sửa Agent. Thêm một Module Proxy/hệ thống ngoài mới = đăng ký tool trên Gateway + cấp policy, Agent không cần biết sự tồn tại của hệ thống đó trước đó.

Checklist trước khi go-live

  • Kafka: DLQ, idempotent consumer, giám sát lag theo case_id đã thiết lập.
  • AgentGateway: policy AuthN/AuthZ, rate limit, và audit log đã áp cho toàn bộ tool + LLM route.
  • Backend: API UI và tool cập nhật kết quả tách quyền đọc/ghi rõ ràng.
  • Knowledge: nguồn dữ liệu ingest có gắn source_refs, không có "tri thức" không truy được gốc.
  • LOS: compliance.* vẫn là chốt chặn cuối cho mọi nội dung tín dụng, không bị Gateway bỏ qua.
  • Có kịch bản replay/resume cho một case khi Agent hoặc Backend gặp lỗi giữa quy trình.

Phân công 2 team dev

Chia theo đúng ranh giới module, không chia theo "ai giỏi cái gì" giữa chừng: Team AI Agent sở hữu toàn bộ phần điều phối/agent/tri thức (Module 1, 2, 3, 5); Team LOS sở hữu toàn bộ nghiệp vụ tín dụng (Module 4) — vì đây là phần LOS đã mạnh sẵn và không nên để team AI làm lại.

● Team AI Agent ● Team LOS

ModuleTeamĐầu việc cụ thể
1 · Backend tiếp nhận AI Agent Kafka consumer (case.intake.received), data model Case/Task/TaskResult, API cho UI (GET /cases/{id}/tasks, GET /tasks/{id}/result), tool ghi backend.create_tasks / backend.update_task_result, idempotency & DLQ.
2 · Agent AI Agent Planner/Orchestrator, skill library (spreading, DSCR, pháp lý, TSBĐ, tờ trình…), MCP tool client, bộ nhớ phiên, prompt/playbook, đánh giá & cải thiện độ chính xác qua phản hồi.
3 · Knowledge (GraphRAG) AI Agent Pipeline ingest, trích xuất thực thể/quan hệ, graph store + vector index, tool knowledge.* (case tương tự, ghi chú chuyên gia, bài học lịch sử).
4 · LOS & nghiệp vụ LOS Toàn bộ danh mục tool nghiệp vụ (document.*, spreading.*, bureau.*, party.*, collateral.*, creditmemo.*, workflow.*, notify.*, audit.*, compliance.*, los.get_loan_plan, los.get_rm_updates), Approval Broker, policy-as-code cho compliance.*, và phát sự kiện Kafka case.intake.received khi RM chuyển hồ sơ sang bước "Thẩm định".
5 · AgentGateway AI Agent (vận hành) + LOS (đăng ký tool) Team AI Agent dựng & vận hành hạ tầng Gateway: registry, AuthN/AuthZ, định tuyến LLM, policy, audit log. Team LOS chỉ cần đăng ký schema/quyền cho các tool thuộc namespace los.* / compliance.* của mình lên Gateway — không cần biết Agent gọi tool như thế nào.

Hợp đồng giao diện — 2 team phải cùng chốt trước khi code

  • Schema message Kafka case.intake.received — LOS team là bên phát (publisher) khi chuyển bước hồ sơ; AI Agent team là bên nhận (consumer). Hai bên chốt field, không đổi ngầm.
  • Schema tool los.* / compliance.* — LOS team định nghĩa input/output, AI Agent team review theo góc nhìn "skill cần gì" để tránh tool thiếu trường agent phải dùng.
  • Mã lỗi chuẩn hoá — LOS trả lỗi phân loại được (thiếu quyền / thiếu dữ liệu / vi phạm chính sách / quá hạn mức) theo nguyên tắc đã có ở agent-los-architecture.html, để Agent xử lý đúng không "đoán".
  • Bảng ánh xạ skill ↔ tool — mỗi skill của Agent Team khai báo rõ cần tool nào của LOS Team; khi LOS đổi tool (thêm trường, đổi version) phải báo trước qua Schema Registry.
  • SLA tool — LOS team cam kết thời gian phản hồi cho từng tool nghiệp vụ (đặc biệt bureau.*, compliance.evaluate) vì Agent chạy theo luồng đồng bộ trong một task.
Không nên làm: để Team AI Agent tự viết logic nghiệp vụ tín dụng (giới hạn cấp TD, thẩm quyền, DSCR tối thiểu…) ngay trong skill/prompt — mọi thứ thuộc Module 4 phải gọi qua tool của Team LOS (compliance.*), đúng nguyên tắc "Agent không tự diễn giải chính sách" đã đặt ra ở tài liệu kiến trúc trước.
Đây là bản thiết kế kiến trúc ở mức khái niệm (prototype). Tên tool, message Kafka, schema và policy trong tài liệu là minh hoạ để thống nhất cách chia module — không phải đặc tả kỹ thuật cuối cùng. Ranh giới trách nhiệm giữa Agent và LOS (Agent đề xuất, con người quyết định) như mô tả trong agent-los-architecture.html vẫn áp dụng cho toàn bộ nền tảng 5 module này.
